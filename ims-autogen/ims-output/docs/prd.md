# 进销存管理系统（IMS）产品需求文档

> 版本：v1.0 MVP | 作者：Alice | 日期：2025-01-21

---

## 一、项目背景与目标

### 1.1 背景
中小型商贸/零售企业在日常运营中面临进、销、存三个环节数据割裂的问题，库存无法实时反映真实情况。现有方案多为手工记账或 Excel 管理，效率低、易出错。

### 1.2 目标
构建一个本地运行的进销存管理系统（MVP），实现：
- 采购入库和销售出库**直接驱动库存变更**，杜绝手动改库存
- 实时库存查询与低库存预警
- 基础进销存报表，辅助经营决策

### 1.3 核心原则
> **库存数据一致性**：采购入库 = 库存增加，销售出库 = 库存扣减。库存数据只能通过业务单据驱动变更，不允许直接修改库存数量。

## 二、用户画像

- **使用者**：小店主 / 个体经营者（单人使用）
- **使用场景**：日常在店铺电脑上管理商品、录入采购和销售、查看库存
- **技术能力**：会用浏览器和基本电脑操作
- **MVP 阶段**：无角色权限，单人操作

## 四、业务流程

### 4.1 核心业务闭环

```
供应商 ──→ 采购订单 ──→ [入库确认] ──→ 库存 +N
                                          │
                    商品信息 ◄─────────────┤
                                          │
客户   ←── 销售订单 ←── [出库确认] ←── 库存 -N
```

### 4.2 采购流程

```
1. 用户创建采购订单
   - 选择供应商
   - 添加商品明细（商品、数量、单价）
   - 订单状态：待入库
   
2. 用户执行入库确认
   - 全部入库：订单状态 → 已完成
   - 部分入库：订单状态 → 部分入库，记录已入库数量
   - 系统自动增加对应商品库存
   - 系统记录库存流水（来源：采购入库）
```

### 4.3 销售流程

```
1. 用户创建销售订单
   - 选择客户
   - 添加商品明细（商品、数量、单价）
   - 校验库存是否充足（预警但不强制阻止）
   - 订单状态：待出库
   
2. 用户执行出库确认
   - 全部出库：订单状态 → 已完成
   - 部分出库：订单状态 → 部分出库，记录已出库数量
   - 系统自动扣减对应商品库存
   - 系统记录库存流水（来源：销售出库）
```

### 4.4 库存预警流程

```
1. 商品信息中设定库存下限（最低库存量）
2. 每次库存变更后，检查当前库存是否 < 下限
3. 如果低于下限，在库存查询页面高亮标记该商品
4. 提醒用户及时补货
```

## 五、数据模型概要

### 5.1 核心实体

```
商品 (Product)
├── id, name, code, category_id, unit_id
├── purchase_price, sale_price
├── stock_low (库存下限)
└── created_at, updated_at

分类 (Category)
├── id, name, parent_id
└── created_at

单位 (Unit)
├── id, name
└── created_at

供应商 (Supplier)
├── id, name, contact, phone, address
└── created_at

客户 (Customer)
├── id, name, contact, phone, address
└── created_at

采购订单 (PurchaseOrder)
├── id, order_no, supplier_id
├── status (待入库/部分入库/已完成/已取消)
├── total_amount
└── created_at, updated_at

采购明细 (PurchaseOrderItem)
├── id, order_id, product_id
├── quantity, received_quantity (已入库数量)
├── unit_price, subtotal

销售订单 (SaleOrder)
├── id, order_no, customer_id
├── status (待出库/部分出库/已完成/已取消)
├── total_amount
└── created_at, updated_at

销售明细 (SaleOrderItem)
├── id, order_id, product_id
├── quantity, shipped_quantity (已出库数量)
├── unit_price, subtotal

库存流水 (StockTransaction)
├── id, product_id
├── type (采购入库/销售出库/其他)
├── quantity_change (+/-)
├── reference_type, reference_id (关联单据)
└── created_at
```

### 5.2 关键约束

- 库存数量 = SUM(所有入库) - SUM(所有出库)，不单独存储，通过流水实时计算
- `received_quantity ≤ quantity`（采购明细）
- `shipped_quantity ≤ quantity`（销售明细）
- 出库时 `shipped_quantity ≤ 当前库存`（软约束，允许超卖但需提示）

## 六、非功能需求

| 类别 | 要求 |
|------|------|
| **性能** | 本地单机，数据量 < 10 万条，所有操作响应 < 1 秒 |
| **可用性** | 浏览器直接打开，无需安装、无需命令行 |
| **兼容性** | 支持 Chrome/Edge/Firefox 最新版本 |
| **数据安全** | SQLite 本地存储，用户自行备份数据库文件 |
| **可扩展性** | 数据模型预留 `created_by` 字段，架构支持未来扩展多人权限 |

## 七、验收标准

### 7.1 核心场景验收

| 场景 | 验收条件 |
|------|----------|
| 商品入库 | 创建采购订单 → 入库确认 → 库存增加，流水可追溯 |
| 商品出库 | 创建销售订单 → 出库确认 → 库存扣减，流水可追溯 |
| 库存预警 | 库存低于下限时，查询页面高亮显示 |
| 数据一致性 | 库存数量始终等于所有流水记录之和，无偏差 |

### 7.2 UI/UX 验收

- 页面响应流畅，无明显卡顿
- 表单校验完善，错误提示友好
- 列表支持分页或合理的数据展示
- 移动端不做硬性要求，但布局不应严重错乱

## 九、附录：术语表

| 术语 | 说明 |
|------|------|
| 入库确认 | 将采购订单中的商品正式计入库存的动作 |
| 出库确认 | 将销售订单中的商品正式从库存中扣减的动作 |
| 库存流水 | 记录每次库存变更的明细日志 |
