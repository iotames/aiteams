# 进阶技巧参考

> 本文件为**低频参考**。仅在需要更严格的技能版本对比、或进行数据洞察时读取。
> 日常迭代通常不需要这些机制——人类审查循环（测试 → 查看器 → 反馈）已足够。

---

## 盲比（Blind Comparison）

需要严格对比两个版本（如"新版本真的更好吗？"）时，可用盲比系统。

基本思路：给独立 agent 两个输出，**不告知哪个来自哪个版本**，让其仅凭输出质量评判胜负。然后分析胜者为何胜出。

### 相关 agent 说明

- `agents/comparator.md` — 盲比裁判：阅读 A/B 两个输出，按内容/结构双维度评分（1-5），判定 winner
- `agents/analyzer.md` — 事后分析：结合胜负、双方技能和 transcript，提炼"胜者强在哪、败者弱在哪"、生成改进建议

### 工作流

1. 同时跑两个版本的输出（可用同一组 eval prompt）
2. 阅读 `agents/comparator.md`，spawn 盲比 agent，输入两个输出路径，得到 `comparison.json`
3. 阅读 `agents/analyzer.md`，spawn 分析 agent，输入 comparison.json + 双方技能路径 + 双方 transcript，得到结构化改进建议
4. 根据建议改进技能，可再迭代

可选功能，需要子任务支持。大多数用户不需要。

## 分析 Benchmark 结果

`agents/analyzer.md` 的「分析 Benchmark 结果」部分专门讲如何解读汇总数据。要点：

- **无区分度断言**：某断言在两个配置下都 100% 通过 → 测不出技能价值，考虑替换
- **高方差评测**：某个 eval 通过率波动大 → 可能不稳定或依赖模型，需要检查
- **时间/token 权衡**：技能是否显著增加耗时或 token？提升是否值得？
- **读 transcript 而非只看输出**：agent 是否在无谓步骤上浪费时间？多个测试是否重复造了同样的辅助脚本（→ 应内置到 scripts/）？

## 改进思路补充

1. **从反馈中泛化**：技能要能用于大量不同场景，而非仅适配几个测试用例。与其做琐碎的过拟合修改或严苛的"必须"，不如尝试不同思路或工作模式。
2. **保持精简**：去掉不发挥作用的内容。阅读完整执行记录——如果技能让模型浪费时间做低效的事，去掉导致这些行为的指令。
3. **解释原因**：解释每项指令背后的**为什么**。如果发现自己用全大写的 ALWAYS/NEVER 或极端僵化的结构，这是警告信号——重新组织语言，让模型理解要求的重要性。
4. **识别重复工作**：阅读测试记录，观察子任务是否都写了相似的辅助脚本。如果多个测试都写了 `create_docx.py` 或 `build_chart.py`，技能应该内置该脚本，放在 `scripts/` 中。
