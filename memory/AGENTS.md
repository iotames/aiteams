## 规则导航

为防止一次性加载过长上下文，低频章节已下沉至 `rules/` 子目录，涉及对应任务时必须先读子文件：
- 执行长命令/长查询 → rules/long-command-reporting.md
- 写代码/脚本 → rules/coding-standards.md
- Git 提交前 → rules/git-commit-check.md
- Git 推送（多远程须全部成功、失败每分钟重试）→ rules/git-push-retry.md
- 查本地软件 → rules/cli-conventions.md
- 定时/后台/cron 等自动化任务 → rules/no-token-waste.md
- 启动端口监听或其他守护进程 → rules/background-processes.md
- 下载依赖、访问外网 → rules/cn-network.md
- 派发子 Agent → rules/subagent-transparency.md
- Markdown 转 PDF → rules/md-to-pdf.md
- 被问及 Agent 自身 → rules/agent-self-questions.md

> **重要**：进入 `rules/` 前先判断路径是否存在，存在则正常查找。不存在则 `AGENTS.md` 可能是默认全局路径下的符号链接，先解析真实路径再找其 `rules/` 子目录。
> **硬性边界**：查找或解析成功即视为已定位，必须按真实路径继续。禁止再大范围搜索找 `rules/`。解析无果才询问用户。

不可乱挑刺以证明自己。

## 语言偏好

1. **使用简体中文**：所有回答、注释、文档、commit message 必须使用中文。代码标识符保持工程化英文惯例。
2. **简洁明确**：回答必须务实、简洁、精准。不扩展未询问的内容。
3. **交互式对话确认**：先问再做，优先使用交互式对话，明确用户需求。

> 记忆文件写入前，必须先回忆或阅读 `记忆文件和上下文` 小节的规则

## 记忆文件和上下文

1. **简明扼要（非常重要）**：上下文过长会稀释关键指令，导致忽略或执行偏差。记忆和指令只保留可落地要点，写前自检长度，能短则短。元数据只保留 `type`，不记录会话 ID。
2. **禁止重复**：写入新记忆条目前，先读一遍现有内容，存在语义重复则改/合/跳过，不盲目追加。
3. **自动触发**：用户输入包含 `记住`, `不要忘`, `以后`, `凡是`，`记忆` 等关键词时，都要判断是否存在更新记忆文件的意图。确认则写入更新，否则向人类询问。
4. **判断记忆作用范围**：新增记忆时，先判断其作用范围。除非和项目强相关，推荐记忆到全局。不确定要提问。
5. **说明理由**：记忆规则附上 Why（为什么这样要求），便于模型理解意图、提升执行力。
6. **指引方向，不设定路**：规则只给目标、原则与边界，不锁死具体命令或路径。环境与工具有无穷可能（Linux/Windows/有无某工具），锁死单一路径必在某环境失效。
   - 落地：读/写规则时，只按“先做什么、再做什么、禁止什么”定顺序与边界；文中出现具体命令或路径，一律当作“示例”而非唯一解，临场按当前环境选可用工具。
   - Why：规则越细越依赖特定环境、越易失效；给方向才跨环境可持续。

## 工作流规则

1. **提交须经确认**: 用户没明确说"提交/commit"，绝不执行 git 写入操作。
2. **文档同步**：修改代码后同步更新相关 .md 文档（README.md、USAGE.md、AGENTS.md 等）。
3. **先问再做（人工交互模式）**：凡有疑问、歧义或多种理解可能，动手前先提问澄清需求，确认后再执行；复杂任务先出方案，认可后实施。
   - Why：澄清成本远低于返工成本，猜错方向会浪费整轮工作。
4. **工程化优先于取悦用户**：代码和命令行操作，以符合工程化最佳实践为准。用户提出不合工程规范的需求，必须主动提出建议和理由，而非盲目执行。
5. **正面回答优先**：用户明确提问时，优先正面回答，不得绕过问题去做别的操作。
6. **长命令/长查询实时播报**：命中 rules/long-command-reporting.md 触发条件的命令，执行前先说明预期动作、耗时、用途，执行后补报实际耗时。细节见 rules/long-command-reporting.md。

涉及 Git 提交时，先读 rules/git-commit-check.md（提交前必须执行自查）。

## 代码规范

1. **全局与局部严格解耦**：全局公共区域/公共组件（如顶栏、导航、全局横幅、公共布局框架）只放所有页面完全一致的全局常驻项；**禁止**按页面显隐、增删或修改全局元素，页面/局部代码不得直接操作全局区域（供数据须经全局模块提供的接口）。页面局部功能放各页面内部，不进全局。适用于任何存在"全局/局部"层级的场景，不限于 WebUI（菜单、弹层、配置框架同理）。
   - Why：全局的定义就是"处处一致"；每个页面看到的全局长得不一样，说明"全局"名存实亡，是架构缺陷而非功能差异。靠页面侧临时开关全局元素会随页面增多而失控，必须从结构上杜绝。

## 用户隐私和数据安全

- 除非用户同意，LLM大语言模型的输入tokens不能包含敏感数据。例如，不写执行后，可能暴露隐私风险的程序和脚本，让大模型作为输入的读取。隐私数据仅在本地流转，不能出外网。
- 所有文件，包括但不仅限于：代码，各种注释，各种文档，隐私数据都应脱敏处理。

## 操作范围与命令精度

1. 严格按用户指令范围操作；范围外事项只报告、不擅自处理，扩大范围前先征得同意。
   - Why：防止偏离意图、浪费时间、触碰隐私。
2. 如命令精确指向目标路径，非必要禁止 -Recurse 等全树扫描。
   - Why：大型依赖目录下全树扫描耗时数十秒，精确路径立即完成。

## 禁止浪费tokens

- 日志或命令输出内容多时，预判并按需读取或搜索，禁止全量读取。如：`npm install`, `mvn install` 等。
- 数据库内容未明确授权不可直接大量读取，防止浪费上下文tokens。鼓励使用 `limit` 限制数量。不推荐 `select *`。

## 本地开发凭据约定

- 本机开发用 MySQL/PG 等服务的弱口令（如 root:root、postgres:postgres）是**有意为之**：供智能体集成测试时自动发现并使用。禁止建议改成强口令。
  - Why：改强口令会导致智能体无法自动发现凭据、测试链路断掉；且把真实凭据写进代码/配置反而引入泄露隐私到代码库的风险。集成测试统一走环境变量（如 MYSQL_TEST_DSN/PG_TEST_DSN）注入，不落库。
